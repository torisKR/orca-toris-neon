# Toris Neon 로드맵

기준: [개발안](Toris_Neon_Development_Plan_2026-11-23.md)(원문은 고치지 않음). 개발안의 PR 1·3·4(이 저장소의 1~3묶음)와 PR 2(4묶음, 토큰 사용량), 6.4절 실행 전 점검(5묶음), PR 5·6(6·7묶음), PR 7 봇·원격 제어 계약(8묶음)은 구현과 테스트를 마쳤습니다. 나머지는 아래 순서로 진행합니다.

## 1묶음: 실행 한도·버전 (구현)

- 하단과 `state.get`에 실행 중인 코드를 표시합니다: 버전, 커밋, 수정 여부, 개발 폴더/설치본(`src/buildinfo.mjs`). `orca-plugin.json` 버전은 바꾸지 않았습니다.
- Neon 전체 배정 한도를 둡니다. 기본값은 동시 2개, 무거운 단계 1개이며 플러그인 설정 `maxActiveJobs`·`maxHeavyJobs`로 바꿀 수 있습니다(1~8, 무거운 작업은 동시 작업 수 이하). 실행별 한도 위에 적용되고, 실행끼리 차례로 배정받습니다(`src/scheduler.mjs`). Neon이 배정하는 작업에만 적용됩니다.
- 일시 정지는 "새 배정 멈춤"이며, 작업 중인 에이전트는 계속 작업한다고 표시합니다. 취소는 세 상태로 나눕니다: 취소 요청 처리 중, 취소 완료(Orca가 종료를 확인함), 종료 확인 필요.
- 대기 중인 단계는 실제 이유를 보여 줍니다. 에이전트 탭에는 한도 대비 현재 수를 표시합니다.
- 실행 카드에서 실행별 정리 결과(닫음·실패·남김)를 볼 수 있습니다.
- 단계별 `instructions`·`description`을 생성·저장·재시작 후에도 보존하고 지시에 넣습니다.
- 쓰기 단계는 커밋을 남겨야 통과합니다. 검토는 그 커밋에 묶입니다(`src/commitcheck.mjs`).

## 2묶음: 기존 앱 개선 (구현)

- 개선 종류마다 짧은 그래프가 있습니다: 오류 수정, 기능 추가, 디자인, 성능, 유지보수, 출시. 결제와 상품 등록은 기능 추가의 선택 항목입니다.
- 앱 정체성 확인 보고를 이후 모든 지시에 넣습니다. 저장 데이터가 있으면 기존 데이터를 여는지 확인하는 것이 필수 검증입니다.
- 진단만 하기: 근거 있는 후보 3~5개를 내고, 후보를 고르면 그 종류의 개선 실행을 연결해 만듭니다.
- 양식에서 새 앱, 기존 앱 개선(종류 선택), 진단만 하기, 이어하기 중에서 고릅니다. `requestId`가 같으면 기존 실행을 돌려줍니다.

## 3묶음: 결과 카드 (구현)

- 단계·실행 결과 카드는 다음 순서입니다: 바뀐 것, 기준별 충족, 실측 이전/이후, 실행한 검증, 검증하지 못한 것, 이 결과 더 개선하기.
- 결과 파일(이미지·짧은 영상·로그)은 누를 때 하나씩 읽습니다. 보고서가 기록한 파일만, 실행 결과 폴더·작업 공간 안에서만 읽습니다. 시안과 실제 화면은 따로 표시합니다.
- "이 결과 더 개선하기"는 `parentRunId`로 연결한 새 실행을 만듭니다. 이전 실행은 덮어쓰지 않습니다.
- 검토 실패는 코드 결함, 검증 부족, 외부 조건으로 나눕니다. 검증 부족은 빌드를 다시 하지 않고, 외부 조건은 재시도하지 않습니다.
- 완료 단계: 구현 결과 생성 → 검증 완료 → 출시 준비 완료 → 내부 테스트 제출 확인 → 프로덕션 게시 확인. 게시 확인은 Play 관측값으로만 표시하고, 관측한 트랙·versionCode·상태·시각을 함께 보여 줍니다. Play의 게시됨은 100% 배포가 아니며, 단계적 출시 비율은 확인하지 않는다고 적습니다.

## 4묶음: 토큰 사용량 (개발안 PR 2, 6.6절, 구현)

- 실행 카드, 단계 상세, 에이전트 카드, 완료 결과 카드에 `1.3M`·`245K`처럼 표시합니다. 단위는 1K=1,000, 1M=1,000,000, 1B=1,000,000,000이고, 소수점은 최대 한 자리이며 `.0`은 붙이지 않습니다. 반올림해서 1000K가 되면 1M으로 올립니다. 숫자를 누르거나(Enter·Space 포함) 펼치면 정확한 정수와 범위, 마지막 확인 시각이 나옵니다(`panel/tokens.mjs`).
- 출처는 Orca의 `agent.listSessions`(host API 1.9)입니다. 실행할 때 `orca.host.has`로 지원 여부를 확인합니다. 기존 60초 감시 주기에 붙어 작업 공간마다 한 번만 조회하고(최대 200개), 끝난 실행은 두 번 더 확인한 뒤 조회를 멈춥니다. 보관한 실행은 조회하지 않습니다. 대화 기록 스캔이나 별도 서버는 없습니다(`src/usage.mjs`).
- 실행의 배정에 연결된 세션만 셉니다(agent + sessionId, hostId는 처음 관측할 때 고정). 누계는 세션별 최신값으로 저장하고 관측값끼리 더하지 않습니다. 배정 시작 뒤에 만들어진 세션은 기준값 0에서 셉니다. 이전부터 있던 세션은 지시를 입력하기 전에 본 값을 기준값으로 삼고, 기준값이 없으면 `세션 누계`로만 보여 주고 실행 합계에는 넣지 않습니다.
- 실패·취소·재시도한 시도도 합계에 들어갑니다. 재시도분은 그 합계의 일부로 따로 보여 줄 뿐 다시 더하지 않습니다. 여러 단계가 한 세션을 함께 쓰면 그 세션은 한 번만 세고 `단계 미분류`로 둡니다.
- 다음 경우에는 0이나 완료로 표시하지 않고 마지막 값을 유지한 채 범위를 좁힙니다: 조회 한도 초과, 목록에서 빠진 세션, 조회 실패, 미지원 Orca, 의미가 불분명한 0, 세션이 확인되지 않은 배정. 표시는 `일부 집계`·`집계 대기`·`집계 불가` 중 하나입니다. 이전보다 작은 값은 연속 두 번 보일 때 보정으로 받아들입니다. 0은 보정으로 받아들이지 않습니다.
- 한계: 원장은 저장 압축에서 줄이지 않습니다(배정 수만큼만 커짐). 세션이 잡히기 전에 압축으로 사라진 배정은 `일부 집계`로 남습니다. 조회가 15초 안에 답하지 않으면 실패로 처리하고, 감시는 다음 주기에 계속합니다.
- 사용량은 실행 원장(`run.usage`)에 들어 있어 재시작과 저장 압축 뒤에도 남습니다. 보관할 때는 계산된 요약만 남깁니다. 조회 시각만 바뀌었을 때는 저장하지 않습니다.

## 5묶음: 실행 전 점검 (개발안 6.4절, 구현)

- 실행 카드를 열 때와 시작 직전에 아직 통과하지 않은 단계마다 **실행 가능 / 해당 단계 불가 / 확인 필요**를 표시합니다. 같은 문제는 한 번만, 걸리는 단계 이름과 할 일을 함께 보여 주고, `다시 점검`으로 새로 확인합니다(`panel/preflight.mjs`). 점검은 알리기만 하며 시작을 막지 않습니다.
- 확인하는 것(`src/preflight.mjs`, `src/hostprobe.mjs`): Orca 프로젝트가 로컬 Git이고 커밋·기준 브랜치가 있는지, 스택 표시 파일, 스택과 단계에 필요한 도구(Flutter SDK, Godot 실행 파일과 내보내기 템플릿, Android SDK·JDK), 제출 단계의 릴리스 서명 설정, 업로드 도구(fastlane·bundletool), Play 제출 계정 연결.
- 단계별 필요 조건: 빌드·테스트·재현·측정·결제 연동·제출 단계는 스택 SDK, 테스트·제출 단계는 APK/AAB를 만들 Android SDK·JDK(Godot은 내보내기 템플릿과 Android 프리셋도), 제출 단계는 서명·업로드 도구·Play 계정. 정체성 확인 단계는 SDK가 없어도 `확인 필요`까지만 표시합니다.
- `해당 단계 불가`는 확실한 근거가 있을 때만 씁니다. 도구 위치는 에이전트 터미널과 같도록 로그인 셸(`$SHELL -ilc env`, 5초 제한)에서 PATH와 SDK 위치 변수만 받아 확인하고, 셸이 답하지 않으면 Orca의 PATH만 보고 찾지 못한 도구를 `확인 필요`로 둡니다. macOS의 `/usr/bin/java`는 JDK가 없어도 있으므로 `java_home`이나 실제 JDK 폴더(Android Studio 내장 포함)만 셉니다. 릴리스가 디버그 키로 서명되도록 설정된 경우만 서명을 `불가`로, 설정을 찾지 못한 경우는 `확인 필요`로 둡니다. 업로드 도구나 Play 계정이 없으면 사람이 Play Console에서 올리거나 준비만 할 수 있으므로 `확인 필요`입니다.
- 빌드는 하지 않습니다. 각 확인은 10초 안에 답하지 않으면 `확인 필요`가 되고, 결과는 실행마다 1분 동안 재사용합니다. `key.properties`는 있는지만 보고 읽지 않으며, 셸 환경에서 PATH·JAVA_HOME·ANDROID_HOME·ANDROID_SDK_ROOT 외의 값은 버립니다. 선택 기능(ECC, 이미지 스킬)은 점검하지 않으므로 단계를 막지 않습니다.
- 한계: Godot 템플릿 버전이 설치된 Godot 버전과 맞는지, Flutter가 프로젝트의 `.fvm` SDK만 쓰는 경우, 서명 키스토어 파일이 실제로 유효한지는 확인하지 않습니다. 새 앱의 빈 저장소는 앱이 생긴 뒤에 서명을 다시 점검하라고 표시합니다.

## 6묶음: 개선 템플릿 심화 (개발안 PR 5, 4.2~4.5절, 구현)

- **디자인 개선**: 디자인 단계는 실제 앱에서 캡처한 변경 전 화면(label `screenshot`)과 촬영 조건 `comparison.before`(기기·화면 크기·언어·데이터)를, 검증 단계는 같은 조건의 변경 후 화면과 `comparison.after`를 보고해야 통과합니다. 이미지에는 모두 label이 있어야 하고 시안은 `mockup`(시안)으로 표시합니다. 결과 카드는 두 조건을 나란히 보여 주고, 다르면 어떤 조건이 어떻게 다른지 경고합니다(`src/kinds.mjs`, `panel/kindresult.mjs`).
- **성능 최적화**: 기준 측정 단계는 `measurement`(시나리오·환경·표본 수·지표별 실제 값 전부)를 보고해야 통과합니다. 검증 단계 지시에는 기준 측정의 시나리오·환경·표본 수가 그대로 들어가고, 재측정이 다른 조건이거나 지표가 빠지면 보고서를 받지 않습니다. 결과 카드는 두 측정이 모두 있고 조건이 같을 때만 중앙값으로 개선율을 계산하며, 그 밖에는 이유를 적고 개선율을 보이지 않습니다.
- **출시 업데이트**: 내부 테스트·출시 단계는 `releaseLink`(소스 커밋·아티팩트·SHA-256·패키지·트랙·versionCode)를 보고해야 통과합니다. 계정은 사용자의 기존 제출 승인에서 연결합니다. 결과 카드는 승인한 패키지·트랙·versionCode, 검토한 커밋, 연결한 Play 앱과 다른 곳을 경고합니다. 실행을 만들 때 같은 프로젝트에서 검증을 통과한 마지막 커밋(검토 시점의 HEAD)을 기록하고, 검증 단계는 그 커밋 이후 바뀐 것만 다시 검증합니다(기록이 없으면 전체). 실제 제출은 그대로 사람의 승인으로만 합니다.
- **이전 결과 재사용 (4.4절)**: 후속 실행은 이전 실행에서 검토를 통과한 단계마다 그때의 소스 fingerprint와 커밋을 기록합니다. 단계를 시작할 때마다 새 작업 공간의 fingerprint와 비교해 같으면 재사용, 다르거나 잴 수 없으면 오래됨으로 표시하고, 지시에 "재사용할 근거"와 "다시 검증할 근거"를 나눠 넣습니다. 결과 카드에 재사용·오래됨 개수를 보여 줍니다(`src/reuse.mjs`).
- **웹 프로젝트**: JavaScript·React·TypeScript 스택이고 Android 대상(Flutter·Godot·Gradle)이 없으면 웹으로 봅니다. 웹 프로젝트의 개선 흐름에는 Play 정책·스토어 자료·상품 등록·결제 연동·제출 단계가 없고(출시 업데이트는 정체성 확인 → 변경 재검증), Play 결제와 Play 앱 연결은 거절합니다. 지시에는 APK/AAB·versionCode·Play 관련 내용이 해당하지 않는다고 적습니다.
- 한계: 촬영 조건과 측정 조건은 에이전트가 적은 문자열을 비교합니다(공백만 정규화). 화면이 실제로 같은 조건에서 찍혔는지는 독립 검토가 확인합니다. 마지막 검증 커밋은 Neon이 기록한 실행에서만 찾습니다.

## 7묶음: 오늘 이어하기·Play Store 연계 (개발안 PR 6, 5.2~5.3절, 구현)

- **오늘 이어하기 (5.2절)**: 실행 카드마다 상태에 맞는 행동 하나를 보여 줍니다(`panel/todayactions.mjs`). 저장·종료·시작 확인 실패(종료 미확인 터미널, 불명확한 작업 공간 생성, 불명확한 시작)는 복구 경로(상태 다시 확인·복구할 단계)를 먼저, 외부 조건(`failureClass: external`, `blocked` 보고, 승인 대기)은 필요한 것과 해당 화면(Play 단계면 Play Store 탭)을, 일시 정지는 `runs.resume`(살아 있는 작업을 먼저 확인)으로 재개를, 완료된 결과(최근 3개)는 "이 결과로 개선"으로 기존 개선 양식을 엽니다. 새 흐름 양식은 열릴 때마다 `requestId` 하나를 가지므로 다시 제출해도 같은 실행이 돌아옵니다.
- **인계 메모**: 검증이 오래된(stale) 메모에는 "바뀐 범위 재검증"이 생깁니다. `today.resume`의 `mode: 'reverify'`가 검증 기록 시점의 HEAD 이후 커밋과 미커밋 변경만 범위로 주고, 영향을 받는 검증만 다시 실행해 실제 실행한 것만 보고하게 합니다(`src/reverify.mjs`). 재검증 에이전트가 살아 있는 동안에는 그 에이전트가 파일을 바꿔도 다시 눌러 새 에이전트를 만들지 않고, 끝난 뒤에는 같은 코드 상태(fingerprint)를 다시 재검증하지 않으며 코드가 바뀐 경우에만 새로 시작합니다. 저장된 인계는 바꾸지 않습니다. 시작 결과가 불명확한 메모는 더 최근 시작이 있어도 그 상태를 먼저 보여 주고, 다시 시작하지 않고 확인할 곳을 보여 줍니다.
- **Play 앱 연결 (5.3절)**: Play 앱(계정 + 패키지)을 로컬 Orca 프로젝트에 사람이 직접 연결하고 플러그인 저장소(`toris-neon.play.links.v1`)에 둡니다(`src/playlinks.mjs`). 앱 이름으로 연결하지 않고, 19자리 개발자 계정 ID가 있는 계정과 그 계정의 패키지 목록에 있는 패키지만, 로컬·비웹 프로젝트에만 연결합니다. 같은 패키지라도 계정이 다르면 다른 연결입니다. 계정 ID가 바뀌거나 패키지·프로젝트가 사라진 연결, Orca 프로젝트 목록을 읽지 못해 확인하지 못한 연결은 문제를 표시하고 아무것도 시작하지 않습니다. 연결 기록이 손상돼도 계정 목록은 그대로 보이고 연결 오류만 따로 표시합니다.
- **Play 작업**: 연결된 앱에서 다음 버전 준비(`release`), 스토어 설명·스크린샷 개선(새 종류 `listing`: 정체성 확인 → 스토어 자료), 정책·권한 점검(새 종류 `policy`: 정체성 확인 → 정책 점검)을 실행 계획으로 만듭니다(시작은 사람이). 같은 작업은 열린 실행이 있으면 그 실행이 열리고, 끝난 뒤에만 새 실행을 만듭니다(`src/playactions.mjs`). 목표에는 계정·패키지·트랙별 versionCode·관측 시각·오래된 관측값 여부가 들어갑니다. 승인되지 않은(rejected) 앱은 Play Console의 실제 반려 사유를 붙여 넣어야 수정 작업을 만들고(새 흐름 양식에서 Play 앱을 연결한 개선도 같은 규칙), 사유 없는 정책 점검·진단은 원인을 추정해 고치지 말라는 지시를 받습니다. 승인 상태를 관측하지 못했으면 목표에 Play Console에서 반려 여부를 먼저 확인하라고 적습니다. 한 번도 관측하지 못한 트랙은 "관측 없음"으로 이름을 적고 오래된 값으로 셉니다. 웹 프로젝트에는 스토어 자료·정책 점검 흐름을 만들지 않습니다. 실행에는 계정 ID와 패키지만 넘기며 Play 조회 키는 넘기지 않습니다.
- **내부 테스트 결과 확인**: 계정을 다시 점검한 뒤 internal 트랙 관측값과, 이 프로젝트에서 검토를 통과한 단계가 기록한 최신 internal `releaseLink`의 versionCode를 제출된 릴리스(심사 중·승인·게시)와 비교해 제출 확인·아직 보이지 않음·오래된 관측·기록된 빌드 없음을 표시합니다. 테스터 의견과 사전 출시 보고서는 읽지 않습니다.
- 한계: 이미 열린 Play 작업 실행이 있을 때 반려 사유를 바꿔 다시 누르면 기존 실행이 열리고 새 사유는 반영되지 않습니다(그 실행을 취소한 뒤 다시 시작). 붙여 넣은 반려 사유는 화면을 다시 그리면 지워집니다. 재검증은 인계 메모(작업 공간)에만 있고, 완료된 실행의 근거 신선도는 후속 개선 실행이 시작될 때 확인합니다(6묶음). Play 작업의 담당은 기본값(작업 codex, 검토 claude)이며 실행 카드에서 바꿉니다.

## 8묶음: 봇·원격 제어 계약 (개발안 PR 7, 10절, 구현)

- 하나의 계약을 두 입구로 받습니다: 명령 `neon.remote`(인자 `args`)와 패널 핸들러 `remote.request`(입력 `input`). 둘 다 `src/remote.mjs`의 같은 함수로 갑니다. 인자 없이(명령 팔레트) 부르면 사용법만 돌려줍니다.
- `create`(mode `new-app`·`improve`·`diagnose`, projectId, goal, kind), `followUp`(parentRunId, kind, goal: 이전 실행의 프로젝트에서 `parentRunId`로 연결한 개선), `get`(requestId 또는 runId), `resume`(시작하지 않은 실행은 실행 전 점검을 거친 `runs.start`, 시작한 실행은 `runs.resume`; `expectedRevision`을 주면 실행의 `updatedAt`과 다를 때 충돌). 만들기는 계획만 만들고 시작하지 않습니다. 모르는 항목은 무시하지 않고 거부합니다.
- 중복 방지: 같은 requestId + 같은 내용(모드·프로젝트·목표·종류·이전 실행)은 이미 만든 실행을 돌려주고, 같은 requestId + 다른 내용은 `[conflict]`로 거부하며 기존 runId를 알려 줍니다. 목표 문장만 같은 다른 requestId는 새 실행입니다. 취소된 실행도 돌려주므로 재전달된 메시지가 취소한 작업을 다시 만들지 않습니다. 내용 지문은 `runs.create`의 requestId 키(`remote.<requestId>.<지문 16자>`)에 들어가 재시작·보관 뒤에도 남고, 별도 저장소를 두지 않습니다. 요청은 하나씩 처리해 동시에 온 두 전달이 둘 다 만들지 않습니다. 한계: 보관 한도(최대 100개, 합계 1MiB)에서 밀려 지워진 실행의 requestId는 기억하지 않으므로, 그 뒤의 재전달은 새 실행을 만듭니다. 패널 양식과 Play 작업 버튼은 지금처럼 "같은 키는 같은 실행"을 유지합니다(키가 양식·열린 작업마다 따로 생김).
- 응답의 실행 요약에는 상태, 통과 단계 수, 실제로 끝난 것이 들어갑니다(`src/milestones.mjs`): 구현(제출 단계를 뺀 쓰기 단계), 검증(test 단계), 제출(internal/release 단계가 승인된 Play 대상과 함께 통과; 구조화된 값은 `done`이 아니라 `approved`). 그래프에 없는 단계는 빼고, 제출은 Play 게시가 아니라 승인된 제출까지만 뜻합니다. 자율 실행의 완료 알림도 같은 문장을 씁니다(제목 `실행 완료`, 예: `구현 완료 · 검증 완료 · 제출 안 함(…)`). 알림은 실행마다 한 번입니다.
- `resume` 결과에는 `action: started|resumed`가 있고, 완료·취소된 실행은 `[conflict]`로 거부합니다. 실행 전 점검 실패는 패널과 같이 시작을 막지 않습니다(점검 결과는 실행 카드에 남음). `expectedRevision` 비교는 최선 노력이며 비교와 재개 사이의 변경까지 막지는 않습니다.
- Orca 브리지는 자기가 아는 코드(실측: `conflict`)는 넘기지만 모르는 코드(실측: `not_found`)는 `action_failed`로 바꾸므로, 메시지가 항상 `[conflict]`·`[not_found]`·`[invalid_params]`처럼 코드로 시작합니다. runtime이 던진 오류도 같은 형태로 바꿉니다.

### 같은 Orca 계정의 다른 기기에서 Auto App을 공유하는가

공유되지 않습니다(1.4.271 코드 기준).

- Neon의 실행 상태는 Orca 호스트의 플러그인 저장 파일(`<Orca 사용자 데이터>/plugins-data/<pluginKey>/storage.json`, 맥에서는 `~/Library/Application Support/orca/plugins-data/local.toris-neon/`)에만 있습니다. 런타임의 `storage.get/set`이 이 파일을 직접 읽고 씁니다.
- Orca 계정 로그인(`orcaAccount.*`)이 쓰이는 곳은 코드에서 Orca Relay(휴대폰 페어링 중계)와 봇 소유자 확인이었고, 플러그인이나 `plugins-data`를 동기화하는 코드는 찾지 못했습니다. `orca account`는 에이전트(Claude/Codex) 로그인 관리입니다.
- 다른 기기의 데스크톱은 자기 기기의 플러그인 목록·저장소로 패널을 그립니다(위 표). 그 기기에 Neon을 설치하면 빈 Auto App이 따로 생깁니다. 휴대폰과 웹 클라이언트에는 플러그인 패널이 없습니다.
- 다른 기기에서 이 맥북의 Neon을 다루는 유일한 길은 이 맥북을 서버로 페어링한 뒤 CLI로 `dev request`를 보내는 것이며(개발 폴더 모드에서만), 이것도 실측하지 않았습니다.
